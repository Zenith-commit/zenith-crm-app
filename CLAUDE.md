# Zenith CRM — Project Context

This file is read automatically at the start of every Claude Code session in this repo. It captures standing decisions, conventions, and current status so nothing gets re-explained, guessed, or contradicted across sessions.

## Project

CRM-style job management app for **Zenith Roof Restorations and Replacements Pty Ltd**, an Australian roofing company. Modeled loosely on ServiceM8, with custom features the client requested beyond that reference.

## Tech Stack

- Frontend: Vite + React
- Backend: Supabase (Postgres + Auth + Storage)
- Access control: Row-Level Security (RLS) keyed off `role` on `public.users`
- Repo: https://github.com/Zenith-commit/zenith-crm (private, under Zenith's business GitHub account — not a personal account)

## Roles

Three roles: `admin`, `office`, `technician`.

- **admin / office** — full access to client data, jobs, materials catalog, bundles, job line items (including cost/price/markup), job diary, communications
- **technician** — assigned to jobs only once a job reaches `Scheduled` status (soft rule — not yet enforced in code, needs eventual enforcement); can see job details and diary; on job line items, technicians may see **qty and item name only** — cost, markup, and price must be hidden from them at the query/RLS level, not just the UI

## Conventions

- **Soft-archive, not hard delete** — every catalog-style table (materials_catalog, bundles, etc.) uses an `active` boolean flag instead of deleting rows
- **RLS pattern** — admin/office-only tables follow the same policy shape already proven on `clients`/`jobs`: `admin` gets one `for all` policy (SELECT/INSERT/UPDATE/DELETE), `office` gets explicit SELECT/INSERT/UPDATE policies with **no DELETE** unless the table holds routinely-edited child rows (see `bundle_items` exception below), zero access for `technician`. `materials_catalog`/`bundles`/`bundle_items` originally gave office a blanket `for all` too — narrowed to match on 2026-08-19, see "Hard-Delete / Unarchive" below.
- **item_number** fields are optional and NOT unique (used as a display label, not a key)
- Always verify RLS with a live test against a technician-role test account before marking a table "done" — don't just review the policy definition
- Test accounts already exist for all three roles (admin, office, technician) against the live Supabase project — use these for verification, no need to create new ones

## Job Status Pipeline

`Quote → Work Order → Scheduled → Completed`

## Deployment

**Live on Vercel** (first deploy 2026-08-28), connected to the same Supabase project used for local dev — one environment, no separate staging/prod Supabase project yet. Vercel is connected directly to the `Zenith-commit/zenith-crm` GitHub repo: every push to `main` auto-deploys to the live site, no manual deploy step. Build command `npm run build`, output directory `dist`, env vars (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`) set in Vercel project settings, not committed to the repo.

The app is a client-side SPA using React Router's `BrowserRouter`, so a `vercel.json` rewrite (all paths → `index.html`) was added — without it, a hard refresh or direct link to a non-root route (e.g. `/jobs/5`) would 404 before React Router loads. Confirmed via `npm run build` producing a clean production build with no hardcoded localhost references and only the two Supabase env vars required.

The first auto-deploy failed because the pushing GitHub identity wasn't recognized as a member of the Vercel team (the team is set up under Zenith's account). Fixed by adding that GitHub account to the Vercel team as a Member.

## What's Built (verified, live)

- Schema, auth, RLS for core tables: `users`, `clients`, `jobs`, `job_diary`, `communications` (five of the six original Day 1-2 tables — `job_costs` was also created in Day 1-2 but is being dropped, see below)

- Job list/detail/create/edit

- **Materials & Services catalog** (`materials_catalog` table + RLS, list/create/edit UI at `/catalog`, admin/office only) — fully built, tested, pushed to GitHub. Fields: item_number (optional/non-unique), description, item_type (material/service), price, purchase_cost, tax_rate (defaults 10% GST), price_includes_tax, active flag.
- **`bundles` table + RLS** — reusable job-type template library, admin/office only. Fields: item_number (optional/non-unique), name, description, active flag. RLS verified live (admin insert, office update/archive, technician blocked).
- **`bundle_items` table + RLS** — line items belonging to a bundle, each referencing a `materials_catalog` row via FK, with default_qty (numeric, can be 0) and default_markup_pct. No `active` flag (line removal is a hard delete) and no sort_order column (displays in insertion order). Admin/office only. RLS verified live (admin insert, office insert+update, technician blocked with visible_count = 0).
- **Bundle management UI** (`/bundles`, `/bundles/new`, `/bundles/:id`, admin/office only) — fully built, manually verified, pushed to GitHub. `BundleList` shows a status column and originally showed both active and archived bundles unfiltered, unlike the Catalog list — since superseded by the hide-archived-by-default toggle below. `BundleForm` + `BundleLineItemsEditor` provide an in-memory editable line-item table (add/remove rows from an active-only materials picker, live per-row price/total, running Total Cost / Total Markup [$ and %] / Total Price footer). Line-item cost formula: `cost_inc_gst = materials_catalog.purchase_cost` directly (confirmed GST-inclusive, no `tax_rate` applied on top). Edit-mode save reconciles the in-memory array against `bundle_items` by `id` (sequential insert/update/delete calls, not a transaction — a known, accepted limitation shared with the rest of this app). Archive is one-way (`active = false` behind a confirm step, no unarchive UI yet). Spec: `docs/superpowers/specs/2026-08-12-bundle-management-ui-design.md`; plan: `docs/superpowers/plans/2026-08-12-bundle-management-ui.md`.
- **`job_line_items` table + RLS + `get_my_job_line_items()` RPC** — the actual per-job billing lines (copied from a bundle or added as one-offs). Fields: job_id, materials_catalog_id (nullable, for one-off lines), item_code_snapshot, item_name_snapshot, qty, cost_inc_gst_snapshot, markup_pct, applied_bundle_id (nullable FK -> job_applied_bundles, added when that table was built), plus stored generated columns price_inc_gst and total_inc_gst. Admin/office full CRUD, same pattern as bundles/bundle_items. Technicians have zero access to the base table — they read qty + item_name_snapshot only through `get_my_job_line_items(job_id)`, a `SECURITY DEFINER` RPC mirroring `get_my_jobs()`, restricted to jobs assigned to them via the existing `technician_owns_job()` helper. RLS + RPC verified live (admin insert, office insert/update/delete, generated columns compute correctly, technician blocked on base table, technician RPC returns qty/name only for their own assigned job and nothing for a job that isn't theirs). `get_my_job_line_items()` was later extended to also return `applied_bundle_id` (see Apply Bundle to Job entry below) — re-verified live after that change, not assumed safe.
- **`job_applied_bundles` table + RLS** — tracks each "a bundle was applied to a job" event, so line items can be grouped by originating bundle and a whole applied bundle removed in one action. Fields: job_id, bundle_id, bundle_name_snapshot, applied_at, applied_by. A bundle can be applied to the same job more than once (each a separate row). `job_line_items.applied_bundle_id` references this table `on delete cascade` — deleting an applied-bundle row removes exactly the line items that belong to it; one-off lines (`applied_bundle_id` null) and other bundles' lines are unaffected. Admin/office only, same pattern as bundles/bundle_items. RLS + cascade behavior verified live (admin full CRUD, office insert+update, technician fully blocked, cascade deletes only the targeted bundle's lines).
- **Apply Bundle to Job** (`BillingSection` on the job detail page, `apply_bundle_to_job()` function) — fully built, manually verified, pushed to GitHub. `apply_bundle_to_job(target_job_id, target_bundle_id)` is the **first write-capable function in this project**: inserts one `job_applied_bundles` header row and one `job_line_items` row per `bundle_items` row as a single atomic call (`SECURITY INVOKER` — buys atomicity via existing RLS, not elevated privilege; a technician calling it directly gets a silent `null`, not an error, since RLS blocks its own internal `bundles` select before either insert runs). Applying an empty bundle is allowed (header row, zero lines). The same bundle can be applied to the same job more than once, each producing its own group. New `get_my_job_applied_bundles()` RPC mirrors `get_my_job_line_items()` so technicians get the same bundle-grouped read-only view (qty + item name only, group names, no cost/markup/price). Grouping/collapsing uses native `<details>/<summary>` — no new dependency. Line items are editable form-style (edit-then-Save per row, not inline), one-off items can be added with a live client-side price preview, and both remove-whole-bundle (deletes the `job_applied_bundles` row, cascade handles its lines) and remove-individual-line actions are confirm-gated, staff only. Spec: `docs/superpowers/specs/2026-08-12-apply-bundle-to-job-design.md`; plan: `docs/superpowers/plans/2026-08-12-apply-bundle-to-job.md`. This completes the Job Billing Integration feature end to end.
- **Client contact info & site address on Job Detail** — `jobs.site_address` (text, nullable) added. `JobDetail` has a new `ClientSiteInfoSection` showing the linked client's name (read-only, links through to `/clients/:id`), phone, and email (from `clients`), plus the job's `site_address`. Both are inline-editable for admin/office as one combined form with a single Save button; under the hood Save fires independent updates to `clients` and `jobs` (no transaction, consistent with the rest of this app's accepted non-atomic multi-table writes), and each reports its own error, so a partial failure (one table succeeds, one fails) is surfaced rather than silently swallowed; the form only closes on full success. A "Copy from Client Address" button fills `site_address` from the client's own `address` on request only, no automatic prefill, starts blank on a new job. Technicians see the same client name/phone/email/site_address, read-only, via the updated `get_my_jobs()` RPC. Required no RLS change (`clients_technician_select` was already row-level, not column-level — technicians could already reach a client's phone/email by navigating to `/clients/:id`, this just surfaces it on the job page too), only extending the RPC's return columns and the frontend queries.
- **`job_type` and `quoted_price` removed from `jobs`** — both columns dropped, along with the `public.job_type` enum type itself, plus every UI/query reference (`JobForm`, `JobRow`, `JobList`, `ClientDetail`'s job-history table, `JobDetail`, `useJob.js`, `useJobs.js`, `jobConstants.js`). `job_type` is fully replaced by `site_address` everywhere it used to appear (Jobs list, job history table); `quoted_price` has no replacement — real pricing now comes entirely from `job_line_items`/bundles, per the original Job Billing Integration design, so the column was redundant. `get_my_jobs()` was drop/recreated (a return-column change, not just `create or replace`) to match, verified live via `pg_get_function_result` against `pg_proc` and a separate technician-impersonation read test, not assumed safe from the DDL alone.
- **Bundle list hides archived bundles by default** — `/bundles` has a "Hide archived bundles" checkbox, checked by default; unchecking restores the original show-all behavior. Pure client-side filter on the existing `active` flag, no schema or RLS change.
- **Job number auto-generation** — `jobs.job_number` (integer, not null, unique), backed by a dedicated `jobs_job_number_seq` sequence (`nextval()` default) rather than an identity column, chosen for explicit backfill control. The 2 pre-existing jobs were backfilled in `created_at` order (#1 oldest, #2 newest) before the sequence was seeded past that max. Assigned at creation for every job regardless of status (including `Quote`), never user-editable. Stored as a plain integer; `Job #0001`-style zero-padded formatting happens client-side only, via `formatJobNumber()` in `jobConstants.js`. Displayed as a new leftmost "Job #" column on the Jobs list and folded into the Job Detail heading (`Job #0001 — {clientName}`). `get_my_jobs()` was drop/recreated to add `job_number` to its return columns (same return-column-change pattern as before) and re-verified live via a technician-impersonation test. No RLS change needed — job_number isn't sensitive.
- **Hard-delete / Unarchive for clients and bundles** — resolves the hard-delete-vs-archive decision. While investigating, found `materials_catalog`/`bundles`/`bundle_items` each had a single office `for all` policy — unlike `clients`/`jobs`, this let office hard-delete rows at the RLS layer (unused by any UI, but a real gap). Narrowed all three to explicit select/insert/update policies, no office delete — same pattern already used for office on `clients`/`jobs`. No new admin policy was needed: `clients_admin_all`/`bundles_admin_all` are already `for all`, which already covered DELETE. **Follow-up correction the same day:** narrowing `bundle_items` broke `BundleDetail`'s existing edit-save flow, which deletes removed line items directly as a routine part of editing (available to office, not just admin) — added `bundle_items_office_delete` back explicitly (not a revert to `for all`), since child line-item rows being deleted/recreated during normal editing is a different thing from hard-deleting a standalone record. Re-verified live after the fix (office edits a bundle, removes a line item, saves, persists after reload). Recorded in `supabase/migrations/2026-08-19_office_delete_gap_and_hard_delete.sql`.
  - **Unarchive** (`BundleDetail`) — admin+office, no confirm, sets `active = true`. Shown in place of the Archive button once a bundle is archived.
  - **Delete Permanently** (`BundleDetail` and `ClientDetail`) — admin-only, confirm-gated, available anytime (not gated behind archiving first — the FK restrict is the real safety net regardless of archive state, so forcing archive-first would only add friction, not protection). Relies on the pre-existing FK constraints (`job_applied_bundles.bundle_id → bundles`, `jobs.client_id → clients`, both restrict) to block deleting anything with real history. On a Postgres `23503` (foreign_key_violation) error, shows a friendly message ("This bundle/client can't be deleted because...") instead of the raw error; any other error still shows the real message. Success redirects to the list page. This is the first place in the frontend with admin-vs-office (not just staff-vs-technician) UI gating.

Goal was to demonstrate the intended UX so a professional developer can finalize the real integrations later.

RLS: admin/office same pattern as everywhere else; technicians get **SMS only, never email** — `communications_technician_sms_select`/`_insert`, scoped via the existing `technician_owns_job()` helper, INSERT restricted to `direction = 'outbound'` (technicians send real SMS but can't fabricate a fake incoming reply — that's a staff-only demo affordance).

Email is staff-only; SMS is staff **and** technician. Each shows a list of past messages (newest first, Sent/Received badge) above a compose form; "Send" logs a row as a simulated success (nothing leaves the app); "Simulate Incoming Reply" (staff-only, hidden from technicians in the UI on top of the DB restriction) inserts a canned inbound row, mainly to demonstrate the notification bell.

Read-state is a single shared `read_at` column, not per-user — matches this app's shared-company-mailbox model (one message, one read state, not "read by me but not you"). Technician branch can't use the admin/office query's embedded `jobs`/`clients` join (technicians have zero `SELECT` policy on `jobs` at all) — resolves job_number via the existing `get_my_jobs()` RPC and client name via a direct `clients` select instead, mirroring the same recipe `useJobs.js` already uses.

Deliberately **not** an open user-directory lookup (that would be a real access regression — technicians can't otherwise see the staff directory at all) — only resolves a name if there's a `communications` row proving the caller is already entitled to know it, mirroring the exact RLS predicate above. Used uniformly by `useCommunications` for all roles now, not just technicians, removing the fragile embedded-join dependency entirely. - **Security hardening pass** — full-stack audit (RLS policies, RPCs, storage policies, frontend) found no live access-control gap; all RLS-protected tables and `security definer` functions confirmed correctly scoped and fail-closed, consistent with every prior live-verified table in this project. - **Invoicing** — real invoice generation built on the already-real `job_line_items` data (not mocked, unlike email/SMS — there's no external system to fake here). Two new tables, `invoices` (`job_id`, `sequence_num`, `paid_amount`, `created_by`, `created_at`, `unique(job_id, sequence_num)`) and `invoice_line_items` (snapshotted from `job_line_items` at creation time — `item_name_snapshot`/`qty`/`unit_price_inc_gst_snapshot`/`total_inc_gst_snapshot`, plus an optional `job_line_item_id` traceability pointer, `on delete set null`), same snapshot pattern as `bundle_items` → `job_line_items`. RLS follows the narrowed admin-`for all`/office-explicit pattern (`clients`/`jobs`/`materials_catalog`/`bundles`), with office getting an **update** policy on `invoices` (needed only for `paid_amount` edits) but no update on `invoice_line_items` (immutable once created) and no delete on either table for anyone — invoices are permanent once generated; voiding one is a documented future item. `create_invoice(target_job_id, line_item_ids)` is the project's second write-capable function after `apply_bundle_to_job()`: inserts one `invoices` header row (`sequence_num` computed as `coalesce(max(sequence_num), 0) + 1` inside the same insert, avoiding a race between concurrent calls on the same job) plus one `invoice_line_items` row per selected id, filtered to the target job so an id from a different job is silently excluded rather than erroring. `security invoker` (the default) — unlike `apply_bundle_to_job()`'s silent-null pattern, a technician calling this directly hits a real RLS policy violation on the header insert, not a null return. All of the above verified live via `do $$ ... raise exception $$` blocks: RLS (admin full CRUD, office select/insert/update-on-invoices-only, no office delete on either table, technician zero access to both), and `create_invoice()` (correct sequence numbering across an admin invoice then an office invoice on the same job, cross-job line-item exclusion, the same `job_line_items` row reused across two invoices without conflict, technician getting a real error not a null). Frontend: `InvoiceSection` mounts on `JobDetail` between `BillingSection` and `DiarySection`, staff only, reusing `useJobBilling`'s already-loaded line items for a checklist-style "pick which lines go on this invoice" creation form (any subset, a line item may be picked for more than one invoice) — `useInvoices(jobId)` hook, `CreateInvoiceForm`. Each invoice row shows `formatInvoiceNumber()`'s `Invoice #0001-A` format (`jobConstants.js`, per-job letter suffix off `sequence_num`, same client-side-formatting precedent as `formatJobNumber`), total/paid/balance due, an editable `paid_amount` (office/admin, direct update), and a "Download PDF" button. PDF generation (`src/lib/invoicePdf.js`, new `jspdf`/`jspdf-autotable` dependencies) is entirely client-side: logo + company details (`src/lib/companyInfo.js` — hardcoded placeholder ABN/address/phone, flagged inline as not real, same "vision demo" standard as the mocked email/SMS sender address) + client "Bill To" block, INVOICE heading, invoice number/date, line-items table, footer totals. GST figures are always derived, never stored (`src/lib/invoiceCalc.js`: ex-GST = `amount / 1.1`, GST component = `amount / 11`, off the existing flat-10%-inclusive project assumption). Manually verified live end-to-end as both admin and office (creation, persistence across reload, paid-amount edit/cancel, PDF content and figures) and confirmed absent for technician. "Send to client" (routing a generated PDF through the mocked email feature), void/delete of an issued invoice, real payment-ledger tracking, and gating creation by job status are all explicitly deferred, not built this phase. Spec: `docs/superpowers/specs/2026-08-25-invoicing-design.md`; plan: `docs/superpowers/plans/2026-08-25-invoicing.md`.
- **Staff Feedback** — first (simplest) item in a larger client-requested feedback list; a minimal free-text feedback mechanism, not a full triage/workflow tool. New `feedback` table (`submitted_by`, `message`, `photo_paths` text array, `created_at` — deliberately no category/type column) + `feedback-photos` storage bucket. RLS departs from this app's usual admin/office pairing in two deliberate ways: (1) `submitted_by = auth.uid()` is enforced on every insert policy except admin's, including office (unlike `job_diary_office_insert`'s precedent, which lets office log without self-attribution — feedback is inherently personal); (2) **view access is admin-only, not admin/office** — office can submit like every other role but cannot read the table or bucket at all, since submissions may include comments about office staff themselves. Both RLS and storage-bucket policies verified live via impersonation (admin full access; office/technician self-attributed insert-only, spoofed `submitted_by` rejected, zero rows/objects visible back, cross-user-folder upload blocked). Frontend: `FeedbackIcon` (compose-only dropdown, all roles, mounted beside `NotificationBell` in `AppShell`) with a client-side photo preview (`URL.createObjectURL`/`revokeObjectURL`, no server round-trip) — no history list shown to anyone from this icon, including admin. `FeedbackInbox` (admin-only page at `/feedback`, admin-only nav link) lists all submissions newest-first with submitter name (direct embedded join via `feedback_submitted_by_fkey` — safe here since only admin ever runs the query, unlike `communications`' `get_sender_name()` workaround) and photos resolved to signed URLs, mirroring `DiarySection`'s existing pattern. ## Current Phase: Job Billing Integration (Day 5-7) — COMPLETE

**Real-world workflow this supports:** customer calls in → inspector visits, writes inspection notes → quoting team selects a pre-built **bundle** (job-type template, e.g. "Concrete Roof Restoration") → bundle's line items get applied to the job → office can freely adjust qty/markup or add one-off items → totals calculate automatically.

**Architecture (four tables — the fourth, `job_applied_bundles`, was added after the original three-table plan to support grouping/bulk-remove):**

1. **`bundles`** — reusable job-type templates (e.g. "Concrete Roof Restoration," "Gutter Installation"). Admin/office only, shared/global library — not per-staff. *(schema + RLS built and verified live)*
2. **`bundle_items`** — line items belonging to a bundle, each referencing a `materials_catalog` row, with a *default* qty (can be 0 — items still show so staff can adjust) and default markup %. Admin/office only. *(schema + RLS built and verified live)*
3. **`job_line_items`** — the actual per-job cost lines. Created by copying a bundle's items onto a specific job, then freely editable (qty, markup, or add new lines not from any bundle). Admin/office full read/write. Technicians: qty + item name only, no cost/markup/price. *(schema + RLS + technician RPC built and verified live)*
4. **`job_applied_bundles`** — one row per "bundle applied to a job" event; `job_line_items.applied_bundle_id` links back to it and cascades on delete, so removing this row is the "remove whole bundle" action. Admin/office only. *(schema + RLS built and verified live)*

**Calculated fields (per line):**
`price_inc_gst = cost_inc_gst × (1 + markup_pct / 100)`
`total_inc_gst = price_inc_gst × qty`

Bundle/job totals are the sum of their line items.
